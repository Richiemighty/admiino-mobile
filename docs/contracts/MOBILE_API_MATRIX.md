# Mobile API Matrix

The P10 workspace contracts below were verified against backend routes, controllers, and services. The mobile app uses the shared P07 API client, which appends `/api/v1` to its configured API origin. No automated state-changing requests were sent to production.

| Mobile flow                | Method and path                                                         | Verified contract                                                                                                                                                                                                                                                                                                         |
| -------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current user               | `GET /auth/me`                                                          | Bearer token required; returns `data.user`.                                                                                                                                                                                                                                                                               |
| Workspaces                 | `GET /auth/workspaces`                                                  | Bearer token required; returns active memberships in `data.workspaces`, including `companyId`, membership `role`, `status`, and workspace details. Listing does not send an active workspace header so stale selection cannot filter membership discovery.                                                                |
| Effective permissions      | `GET /access-requests/me/effective-permissions`                         | Bearer token and `x-company-id` required; returns the selected membership role and effective permission map. Mobile tabs remain unavailable until this response matches the selected workspace.                                                                                                                           |
| Create workspace           | `POST /companies`                                                       | Bearer token required; `{ name }` is sufficient. Backend creates the workspace with its default plan and an active owner membership, then returns `data.company`.                                                                                                                                                         |
| Resolve workspace code     | `POST /companies/join/resolve`                                          | Bearer token required; `{ companyCode }`; returns the workspace name and canonical code.                                                                                                                                                                                                                                  |
| Request to join            | `POST /companies/join/requests`                                         | Bearer token required; `{ companyCode, message? }`; eligible active, verified workspace accounts create a pending request requiring workspace review. A duplicate pending request is returned as accepted without creating another request.                                                                               |
| My join requests           | `GET /companies/join/requests/mine`                                     | Bearer token required; returns only the caller's requests and their statuses. Approval does not itself grant mobile access; membership must appear in the workspaces response.                                                                                                                                            |
| Home assigned-task summary | `GET /tasks/my/summary?relation=assigned`                               | Bearer token and `x-company-id` required; returns `data.summary` with server-computed counts for the caller's assigned tasks in the active workspace. This is not a company-wide aggregate.                                                                                                                               |
| Home assigned-task list    | `GET /tasks?scope=assigned_workspace&relation=assigned&limit=50&page=1` | Bearer token and `x-company-id` required; returns `data.tasks` and `total`. The backend limits results to the caller's assigned tasks and orders the page by creation time; mobile uses only this page for task rows and never derives totals from it.                                                                    |
| Global search              | `GET /global-search?q=...`                                              | Bearer token and `x-company-id` required; `q` is trimmed, limited to 100 characters, and queries shorter than 2 characters return empty groups. Responses contain permission-filtered `data.groups` for tasks, projects, people and other supported entity types. The endpoint is rate-limited to 45 requests per minute. |

P13 project contracts were verified against `admiino-backend/src/routes/projectRoutes.js`, `src/controllers/projectController.js`, `src/controllers/folderController.js`, `src/services/projectAccessService.js`, `src/services/projectFileAccessService.js`, `src/services/projectMutationService.js`, `src/services/workspaceGovernanceService.js`, `src/utils/workspaceEffectivePermissions.js`, and the User Portal project API.

| Mobile flow                       | Method and path                          | Verified contract                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| List projects                     | `GET /projects`                          | Bearer token and `x-company-id` required. Returns `data.projects` and `results`; backend visibility is `view_all_projects` or workspace-visible/active project membership. `search` and `teamId` are supported; search is capped at 50 results and there is no pagination or status query.                                                                                                                                                                      |

Backend checks both active workspace ownership and project visibility/membership; inaccessible workspace records are not enumerated.                                                                                                                                                                                                                                                          |
| Create project                    | `POST /projects`                         | `{ name }` is required. `description`, `visibility`, `leadId`, `color`, `startDate`, `dueDate`, `endDate`, `settings`, and `teamId` are supported. Requires effective `create_projects` and an unrestricted `projectCreationPolicy`; the backend defaults status to `active` and visibility to `private`.                                                                                                                                                       |
| Update project                    | `PATCH /projects/:id`                    | Supports `name`, `description`, `status`, `visibility`, `leadId`, `color`, `startDate`, `dueDate`, `endDate`, `settings`, and `teamId`. The backend permits workspace owners/admins/managers or active project owner/admin members; the mobile edit screen uses effective workspace membership plus verified project membership and still relies on server authorization. Status values: `planning`, `active`, `on_hold`, `completed`, `cancelled`, `archived`. |

Backend checks project access and workspace ownership.                                                                                                                                                                                                                                                                                                              |
| Create task in project            | `POST /projects/:id/tasks`               | Uses the existing task creation payload and requires project access plus effective `create_project_tasks`, independently of `create_tasks`.                                                                                                                                                                                                                                                                                                                     |
| List project members              | `GET /projects/:id/members`              | Returns `data.members` (`id`, `role`, `status`, and user name/email fields) and pending invites. Mobile displays active members only.                                                                                                                                                                                                                                                                                                                           |
| List project files                | `GET /projects/:id/files?folderId=...`   | Returns safe file metadata and folder/breadcrumb data. Backend enforces project access and file scope. Mobile never uses `fileUrl`, `publicId`, or download URLs; project files are displayed without download actions.                                                                                                                                                                                                                                         |
| Project creation governance       | `GET /workspace/governance/capabilities` | Active internal workspace membership required; returns `projectCreationRestricted` and other capabilities. Mobile combines this with effective `create_projects` before exposing Create Project.                                                                                                                                                                                                                                                                |
| Workspace teams for project forms | `GET /team/teams`                        | Bearer token and `x-company-id` required; returns workspace-scoped teams. The mobile app offers team assignment only when effective `assign_workspace_members` is enabled.                                                                                                                                                                                                                                                                                      |

Workspace-scoped calls pass the selected `companyId` through the API client's `workspaceId` option. Permissions are never inferred from the legacy user role.

P14 notification and approval contracts were verified against the current backend routes, controllers, services, and User Portal API/UI. These are source-level findings only; no authenticated production or staging requests were sent.

| Mobile flow                         | Method and path                                                           | Verified contract                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Active-workspace notifications      | `GET /notifications?companyOnly=true&limit=20&offset=0[&unreadOnly=true]` | Bearer token and `x-company-id` required. `companyOnly=true` is mandatory: the default list is cross-workspace. Returns `data.notifications`; `results` is the number of preference-visible rows on this page, not a total. The backend filters notifications whose in-app preference is disabled before returning the page and exposes no raw row count or `hasMore` field.                         |
| Unread count                        | `GET /notifications/unread-count`                                         | Returns `data.count` after user preferences, but counts all workspaces for the signed-in user; the controller ignores active workspace scope. Do not use for an active-workspace Inbox badge. A workspace count can only be derived reliably from the scoped list when all in-app categories are enabled; with any category disabled, preference filtering makes the list's page boundary ambiguous. |
| Mark one notification read          | `PATCH /notifications/:id/read`                                           | Bearer token and `x-company-id` are sent, but the controller authorizes by user ID and notification ID and does not check notification company. Only submit IDs obtained from the current `companyOnly=true` feed, and ignore stale UI responses after workspace changes.                                                                                                                            |
| Mark all notifications read         | `PATCH /notifications/read-all`                                           | Marks every unread notification for the user across all workspaces. It is not safe for a workspace-scoped Inbox; do not call it.                                                                                                                                                                                                                                                                     |
| Delete notification                 | `DELETE /notifications/:id`                                               | Deletes by user ID and notification ID without workspace validation. Do not expose deletion in the active-workspace Inbox.                                                                                                                                                                                                                                                                           |
| Notification preferences            | `GET /notification-preferences`                                           | Bearer token; user-level, not workspace-scoped. Returns seven categories and `data.whatsApp` (`linked`, `globallyEnabled`). Supported channels are `inAppEnabled`, `emailEnabled`, and `whatsAppEnabled`; no push channel or device-registration contract exists.                                                                                                                                    |
| Update notification preferences     | `PATCH /notification-preferences`                                         | Bearer token; body `{ preferences: [{ category, inAppEnabled?, emailEnabled?, whatsAppEnabled? }] }`. At least one boolean channel is required per entry; omitted channels retain their defaults.                                                                                                                                                                                                    |
| Workspace join-request queue        | `GET /companies/join/requests?status=pending&page=1&pageSize=20`          | Bearer token and active `x-company-id`; owner/admin active workspace membership is required. Returns `data.requests` and `data.pagination` (`page`, `pageSize`, `total`, `totalPages`). A request includes requester identity/status, workspace, message, and decision metadata.                                                                                                                     |
| Workspace join-request detail       | `GET /companies/join/requests/:id`                                        | Owner/admin active workspace membership; request is scoped to the active workspace.                                                                                                                                                                                                                                                                                                                  |
| Decide workspace join request       | `PATCH /companies/join/requests/:id`                                      | Body `{ action: "approve" \| "decline" }`; owner/admin only; self-approval is forbidden. Approval creates or activates a verified `member` membership (no team/project access) and can fail on seat limit, suspension, or a stale/ineligible applicant. Decline sets status `denied`.                                                                                                                |
| Pending member verification         | `GET /team/pending-verifications`                                         | Owner/admin only; returns `data.pendingMembers`, unpaginated, scoped by active workspace. Rows include `companyId`, `userId`, membership state, and a user object (password excluded).                                                                                                                                                                                                               |
| Approve member verification         | `PATCH /team/verify/:assistantId`                                         | Path ID is the user ID; owner/admin only. Sets membership `isVerified=true`, `status=active`, and legacy user `isActive=true`, `invitationStatus=approved`.                                                                                                                                                                                                                                          |
| Reject member verification          | `DELETE /team/reject/:assistantId`                                        | Path ID is the user ID; owner/admin only. Sets membership `status=removed`, `isVerified=false`, and also sets the global user account `isActive=false`, `invitationStatus=rejected`. This global account side effect must be stated in the confirmation.                                                                                                                                             |
| Workspace permission-request queue  | `GET /access-requests?status=pending&limit=200`                           | Bearer token and `x-company-id`; active owner/admin/manager memberships see workspace requests. Others receive only their own and cannot decide. Returns `data.requests` with requester, permission key, reason/status and decision metadata; list limit is capped at 200 and has no pagination response.                                                                                            |
| Decide workspace permission request | `PATCH /access-requests/:id`                                              | Body `{ action: "approve" \| "deny" }`; owner/admin/manager active membership only. Approval creates or updates the requested effective `WorkspaceUserPermission`; already-decided requests return an error.                                                                                                                                                                                         |

Notification destinations use verified IDs in notification data (`taskId`/`task_id`, `projectId`/`project_id`, and request IDs for the corresponding request event types). Mobile routes must still load the destination through the existing workspace-protected task/project/approval APIs. No mobile WebSocket client or push-device flow exists; refresh on Inbox focus and app foreground instead of adding a new event channel or polling.

P15 conversation and file contracts were verified against `admiino-backend/src/routes/taskCommentRoutes.js`, `src/controllers/taskController.js`, `src/services/taskCommentIdempotency.js`, `src/services/taskCommentNotificationService.js`, `src/routes/taskAttachmentRoutes.js`, `src/routes/downloadRoutes.js`, `src/utils/fileUploadSecurity.js`, and `src/services/taskAccessService.js`. These are source-level findings; no production requests or mutations were made.

| Mobile flow                                      | Method and path                                                     | Verified contract                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Task conversation page                           | `GET /task-comments/task/:taskId/comments?limit=50&offset=0`        | Bearer token and `x-company-id` are required. Returns `{ success, comments, pagination: { total, limit, offset, hasMore } }`; comments are ordered oldest-first. The mobile app pages backward from the final page, merges by comment ID/client message ID, and refreshes on screen focus and app foreground.                                                                                                                                                            |
| Create comment / reply / mention / comment files | `POST /task-comments/task/:taskId/comments`                         | Multipart fields: required `content`; optional `parentCommentId`; optional `mentionedUserIds` as a JSON string array; optional `clientMessageId`; repeated `files` (maximum 10). The backend verifies task access, reply-parent task membership, and mention IDs against task participants. Comment idempotency is supported by an 8–100 character `[A-Za-z0-9_-]` client ID; retries must reuse the same ID and identical content/parent. Uploads are server-validated. |
| Task details / task attachment metadata          | `GET /tasks/:taskId`                                                | Returns task-level `access` with `canView`, `canEdit`, and `readOnly`; attachment metadata is present without storage URLs. The controller does not expose the access service's `canCollaborate` field, so the mobile composer conservatively requires edit access; permitted read-only collaborators may be denied despite backend support. Do not infer this right from role.                                                                                          |
| Upload task attachment                           | `POST /task-attachments/:taskId/upload`                             | Multipart `file`; bearer token; task-file mutation permission enforced by backend. One file per request. Server validates extension, MIME and file signature; maximum 20 MiB.                                                                                                                                                                                                                                                                                            |
| Download task or comment attachment              | `GET /tasks/:taskId/attachments/:attachmentId/download`             | Bearer token required. The attachment must belong to the task and `canAccessTask` must authorize the caller. Device files are proxied; the private storage URL/public ID is not returned. Google Drive files redirect to the provider URL, so mobile deliberately rejects that source (`redirect: error`) and does not expose or follow it. Mobile downloads are capped at 20 MiB.                                                                                       |
| Mentions and replies                             | Included in comment creation payload                                | Both are supported as above. Mention suggestions are limited to verified task participants and, when a task has a team, active team members returned by workspace membership APIs.                                                                                                                                                                                                                                                                                       |
| Comment edit/delete                              | `PUT /task-comments/:commentId`, `DELETE /task-comments/:commentId` | Backend routes exist, but P15 mobile does not expose edit/delete actions.                                                                                                                                                                                                                                                                                                                                                                                                |
| Realtime conversation                            | WebSocket `join_task` / comment events                              | Backend socket authentication reads the JWT from a query parameter. This is incompatible with the mobile no-token-in-URL security requirement; P15 does not connect to it. HTTP refresh on focus, foreground, pull-to-refresh, and after uncertain sends is the supported fallback; no polling is used.                                                                                                                                                                  |

File uploads support the backend allowlist (PDF, Word, Excel, PowerPoint, plain text/CSV, JPEG, PNG, WebP, and GIF); HEIC/HEIF and SVG are excluded. Comment-level attachments are submitted with the comment and are not displayed as task-level attachments. Mobile does not use `/drive/files/:fileId/download` or the missing task-attachment preview endpoint. Task-level read-only collaboration is a known contract gap because `GET /tasks/:id` omits `canCollaborate`; do not weaken server authorization to work around it.

P16 account contracts were verified against the authenticated profile routes, `/auth/me`, the User model validators, and the User Portal. No production requests or mutations were made.

| Mobile flow            | Method and path                | Verified contract                                                                                                                                                                                                                                                 |
| ---------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Load current account   | `GET /auth/me`                 | Bearer token; returns the authenticated user's safe profile, including name, email, bio and `profilePictureUrl`. It is user-scoped and does not require the active workspace header.                                                                              |
| Update profile         | `PATCH /profile/update`        | Bearer token; accepts supported `firstName`, `lastName` and `bio` fields. Name validators enforce 1–50 characters and bio is limited to 1000 characters. Email changes are not supported by this endpoint.                                                        |
| Upload profile picture | `POST /profile/upload-picture` | Bearer token; multipart field `profilePicture`; maximum 5 MiB. Backend validates file signatures for JPEG, PNG, WebP and GIF and returns `data.profilePictureUrl`. Mobile converts HEIC/HEIF selections to JPEG and checks the resulting file size before upload. |
| Password recovery      | `POST /auth/forgot-password`   | Existing email-based reset flow; not an authenticated change-password API. Mobile can request a reset email but does not collect or persist passwords.                                                                                                            |

No self-service account deletion or deletion-request contract, ownership-transfer policy, or official web deletion flow was found. The only deletion route found is privileged administration and must not be used by the mobile application. B-08 remains a release blocker; the mobile Delete Account screen explicitly reports that deletion is unavailable and submits no destructive request. Sign out is not account deletion.
